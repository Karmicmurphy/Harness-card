## Purpose

Turn an ordinary interactive ChatGPT conversation into Randy's default software command center whenever the available tools are sufficient.

This skill does not pretend Chat has tools or permissions it does not have. It does not bypass product limits, plan limits, authorization, sandboxes, or security boundaries. It makes the most effective use of the tools that are actually available, and delegates only the smallest missing execution step when another runtime is genuinely required.

## Default rule

**Do not send software work to Codex, Work, Astra, or another agent merely because the task contains code.**

Stay in interactive Chat when the current conversation can:
- recover intent;
- inspect the live repository or files;
- edit the required files;
- run or inspect available tests/builds/checks;
- verify the relevant result;
- record authority and handoff state.

Use another execution environment only when a required capability is unavailable here or when a bounded autonomous grind is materially cheaper or safer than interactive execution.

## Trigger phrases

Any of these activate this skill:
- "Chat build mode"
- "Use the chat software harness"
- "Build it here"
- "Do this in chat, not Codex"
- "Use Harness Card and build/fix this"
- equivalent intent that clearly asks Chat to act as the software workshop

The user should not have to name the skill if the situation obviously matches it.

## Core contract

The conversation is the command center.

The agent owns translation from informal human intent into technical execution. Randy does not have to write an engineering prompt, acceptance test, work order, or implementation plan first.

The agent must:
1. recover the real requested outcome from relevant context;
2. identify the live project authority;
3. inspect before modifying;
4. salvage before rebuilding;
5. protect known-good behavior;
6. choose the smallest coherent change;
7. execute with available tools;
8. prove the actual user path;
9. repair failures and retest while progress remains possible;
10. write back durable state so the next chat can resume without reconstruction.

## Operating loop

### 1. INTENT COMPILE

Convert natural language into a temporary internal work contract:

- target outcome;
- observed symptom or requested behavior;
- project/repository;
- branch/ref;
- known constraints;
- target devices/runtimes;
- protected behavior;
- acceptance evidence;
- stop condition.

Do not force the user to restate information already recoverable from conversation, Harness Card, project state, or live repo evidence.

### 2. AUTHORITY LOAD

Load, in order of relevance:
- Harness Card `AGENTS.md`;
- `OPERATING_CONTRACT.md`;
- `state/AUTOGENERATED_RULES.md` when present;
- `state/CURRENT_PROJECT.json` and project index when project identity is unclear;
- the actual project repo's governing handoff/authority files;
- live branch/ref/deploy/device evidence.

Current verified truth outranks chat memory and stale handoffs.

### 3. SALVAGE BEFORE BUILD

Before introducing a new mechanism:
- inspect the current implementation;
- inspect known-good prior implementation when relevant;
- route Artifact Compass when external/current mechanisms should be researched;
- route Artifact Salvage / Deep Salvage when useful mechanisms may already exist;
- route Cost & Complexity Challenge before substantial infrastructure or dependency growth.

Do not replace working code merely because a cleaner rewrite is possible.

### 4. EXECUTE HERE FIRST

Use the tools available in the current Chat session directly.

Typical actions may include:
- repository inspection;
- branch/ref comparison;
- file creation/editing;
- debugging;
- dependency/configuration inspection;
- build/test execution where tools permit;
- deployment inspection or execution where authorized;
- browser/device evidence inspection where available;
- documentation and handoff updates.

A coding task is not automatically a Codex task.

### 5. REPAIR LOOP

When an execution or proof step fails:

`observe -> classify failing layer -> inspect evidence -> smallest repair -> rerun failed gate`

Do not restart the whole project unless evidence shows the architecture itself is invalid.

Do not silently switch to a new framework, agent, repo, or branch.

### 6. PROOF GATE

Never promote implementation directly to DONE.

For software, evidence should progress only as supported:

`CLAIMED -> IMPLEMENTED_UNPROVEN -> PARTIALLY_PROVEN -> PROVEN_IN_TEST -> PROVEN_LIVE`

For user-facing software, apply the Harness Card UI/app hard gate:

`source changed -> tests pass -> deploy succeeds -> live target loads -> intended screen wins after startup settles -> primary user action works -> user-visible result is recognizable -> PROVEN_LIVE`

When target-device proof is unavailable, say exactly which gate remains unproven.

### 7. STATE WRITEBACK

After a material change, update the relevant authority/handoff state with:
- repo;
- branch;
- verified commit/ref;
- what changed;
- evidence state;
- tests/proof run;
- remaining blocker or next unproven gate.

Do not dump private conversation content into public repos.

### 8. CLOSE

End each bounded work order as exactly one of:
- DONE;
- BLOCKED BY <condition>;
- FAILED FOR <reason>;
- RETIRED / ABANDONED ON PURPOSE.

## Delegation gate

Delegation is an exception, not the default.

Only delegate when at least one is true:
- the current Chat lacks a required execution capability;
- a long mechanical change across many independent files would be materially more efficient in an autonomous coding environment;
- the task requires unattended execution that this Chat cannot perform;
- a provider-specific environment is required for the actual proof gate.

When delegation is necessary, produce the **smallest bounded execution packet** possible:

- exact repo;
- exact branch/ref;
- exact target files or scope;
- protected interfaces/behavior;
- required change;
- tests;
- acceptance criteria;
- stop condition;
- requested return evidence.

The external agent is a worker, not project authority. Its output returns to Chat for verification against the governing acceptance contract.

## Anti-waste rules

- Do not invoke a stronger model merely because it exists.
- Do not use autonomous agents to rediscover context already available here.
- Do not rerun broad repository scans after authority has been established unless evidence changed.
- Do not create parallel agents for a single serial problem.
- Do not create new architecture to solve a localized bug.
- Do not confuse token/compute expenditure with engineering quality.
- Prefer one verified move over a large speculative batch.

## Human interaction rule

Randy may say things such as:
- "sound is fucked on my phone";
- "fix the fucking repo";
- "that isn't what I meant";
- "use the thing we already built";
- "make it work on PC and phone."

Treat these as valid problem reports. Recover the technical contract from context and evidence instead of requiring prompt-engineering syntax.

## Fast bootstrap

When the user says **"Chat build mode"**, perform:

1. load Harness Card authority;
2. resolve the active project;
3. verify live repo/ref;
4. recover the current unproven gate;
5. select only needed skills;
6. execute the smallest useful move in Chat;
7. prove it;
8. write back state;
9. stop at the work-order boundary.

## Success condition

This skill is PROVEN when interactive Chat successfully resumes and completes software work on at least two distinct projects, including live authority recovery and proof, without requiring Randy to manually restate the operating process or move the task into Codex merely because code is involved.
